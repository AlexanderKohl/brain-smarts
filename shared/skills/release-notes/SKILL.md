# Release Notes

Read `/CONTRACT.md` first.

## Purpose

Help the owner remember what changed, and tell the team what to expect and what to look out for.
Commits are the developer's record; a release note is the user's.

## What a note is

A release note records **one change someone who uses the system would notice**: something they
now see, do or receive differently, or must watch out for. It is written from their side, in their
words, with no code terms.

- **One note per outcome, never per commit.** Six commits that together change how production is
  estimated make one note. Each commit names its note with the trailer `Release-note: <slug>`;
  the note's `commits` and `versions` are generated from those trailers by `link`, never kept by
  hand.
- **No note** for refactors, tests, tooling, dependency bumps, or fixes no user could have met.
- **The test:** can it be written as "You can now… / X now… / Watch out for…" without a code term?
  If not, it is probably not a note.

## The note file

One Markdown file per note, named by its slug:

```yaml
---
title: Solar production is now estimated from each site's own weather
kind: changed            # added | changed | fixed | removed   (new is read as added)
area: solar calculator
audience: [office, sales]
visibility: undecided    # undecided | announce | hold | internal
look_out_for: >-
  What someone should check or expect to be different.
authors: [Example Tester]
commits: [e506475, 6b048a6]   # generated by `link` from the trailers
versions: [2.41.0, 2.42.0]   # generated by `link`: package.json at each of those commits
workflows: []            # names of outside-system objects the note covers
opened: 2026-09-24
---

Two or three plain sentences from the user's side.
```

A note in the owner's memory also carries the brain's metadata (`id`, `type: release_note`,
`contract`, `created`, `updated`); a note in a project repository does not.

**A note file is written by its author and edited by nobody else.** What the owner chooses –
visibility, a wording change, what to do with a commit no note claims – is a **choice event**:
one file under `<release-notes>/choices/<author>-<UTC stamp>.json`, append-only, never edited,
moved or deleted (`release_choices.py`). The effective note is folded from the file and the
choices on every build, the same way on every brain: for each field the earliest choice
decides; a later choice by the same author replaces their own; a later different choice by
another author does not change the value but is shown on the board as a conflict, so both see
it. At release the chosen wording and visibility are baked into the released copy.

**Visibility.** Every note starts `undecided`. Only the owner moves it: `announce` goes to the
team at the next release; `hold` is kept back and carried forward; `internal` is recorded in
the release and never shown to the team. `undecided` carries forward, so nothing is ever
released by default.

## Projects, boards and team pages

The owner's configuration, `/memory/skills/release-notes/config/release-notes.json`, names:

- **projects** – where notes come from:
  - `kind: git`: notes in `<repo>/release-notes/unreleased/` on the `development` branch.
    Commits in `production..development` that no note claims are listed on the board (`since`
    limits how far back). A `not-user-visible.txt` written before choices became events is
    still read, never written.
  - `kind: folder`: notes written by hand, for example changes made in a CRM's own interface.
    `folder` is a brain path or `<repository>:<path>` – a hand-written source may live inside a
    project repository beside the app's notes (`release-notes/<source>/`), so one checkout draws
    both.
  - `artifact_url`: where the team reads the notes – the application's own route (such as
    `/release-notes`), which renders `released/` for the environment it runs in.
- **pages** – the team pages. One page can show several projects to the same readers; `build`
  writes one file per environment (`<id>.testing.html`, `<id>.production.html`) and `<id>.html`
  as the production view, under `pages_dir`.

**A project the repository defines itself.** A project repository whose board is shared
(CONTRACT section 16.2) keeps its own release-notes projects in `brain/status/release-notes.json`,
so every brain that builds the board draws the notes without the owner's configuration:
`{"projects": [{"id", "label", "kind", "development", "production", "since", "folder"}]}`.
`kind` is `git` (default; `development` and `production` are required) or `folder`; `folder`
(default `release-notes`) is relative to the repository root – an absolute path, a drive, a
`<repository>:` prefix or `..` is refused, and so is a folder whose resolved path leaves the
repository through a symlink or junction. That check runs when the file is loaded, and every
read and write under the folder goes through `Config.inside`, which resolves the final path
(and so every directory created on the way) and refuses it outside the repository: a link at
`unreleased/`, `choices/`, `released/<version>/` or on a note is refused like one at the folder
itself – and the repository is the one that holds the file,
so no `repo` and no machine path is stored. The file holds the project's own facts only, never
a person's. Precedence, highest first: an entry with the same `id` in the owner's memory
configuration, then the repository file of the board being built. A brain without the owner's
file reads an empty memory configuration. A broken repository file, or a refused entry, is a
problem the board shows as a line, never an exception. The command line loads the same way,
through the same `load_config`: `release_notes.py --repo <clone> new|link|check|build|release ...`
adds that repository's projects, and without `--repo` the repository holding the current folder
does, if it has the file; each problem is printed to standard error.

The choosing happens on the project's **board**: a board whose entry in
`/memory/skills/owner-board/config/boards.json` carries `release_notes: ["<project id>"]` draws a
release-notes section (`/shared/skills/owner-board/SKILL.md`, *Release notes on the board*) and
saves the choices with the verdicts. There is no combined selection page any more.

## Procedure

1. **While working.** When work a user would notice starts, open its note:
   `python shared/skills/release-notes/scripts/release_notes.py new <project> <slug> --title "..."`,
   and keep it current as the work changes. Name it in each commit with `Release-note: <slug>`,
   and name it on the board card with `card.py ... --note <slug>` (check 11 of the board asks
   for one when a version raised the first or middle number). Commit the note with the work.
2. **A note that does not parse never stops anything.** `release_notes.py check` names it
   with file, line and problem and exits 1; `release_notes.py fix` (or `check --fix`) repairs
   the common shape, wording and line endings unchanged; `link` and `build` skip a note that
   still fails and say so at the top of their output. `session.py finish` runs `fix`, `link`
   and `build` for every git project on every finish.
3. **Before a release.** `release_notes.py link <project>` fills each note's `commits` and
   `versions` from the trailers (commit the notes it changed). The owner opens the board,
   chooses a visibility for each note, edits the wording in place, deals with commits in no
   note (**New note**, **Add to an existing note**, **Not user-visible**) and presses **Save my
   verdicts**; `apply_events.py` (owner-board) hands the `releaseNotes` part to
   `release_choices.apply_choices`, which writes the choice events. A **New note** choice also
   creates the note, by the author who chose it. Commit the events in their repository.
4. **Release**, per environment, as a step of the project's release checklist:
   `release_notes.py release <version> --env testing` when the version reaches testing, and
   `release_notes.py release <version> --env production` when it reaches production
   (`--project <id>` names a folder source such as the CRM's; `--date` overrides today). The
   first release of a version moves the announced and internal notes into
   `released/<version>/` with a `release.json` that records each environment and date, baking
   the chosen wording in; a later environment only marks the record. A git project refuses
   until every commit of an announced note is on that environment's branch. Then one
   `released` event is written per open board card at or below the version on every board
   that draws the project: a testing release puts the card in the board's *Released* fold, a
   production release retires it on both brains at the next build. `--dry-run` says what would
   happen and writes nothing.
5. **Share.** `build` (run by every finish) rewrites the team pages; the application serves
   the same content at `artifact_url` for its own environment, so testing shows what has
   reached testing and production only what has reached production.

## Not allowed

- Releasing a note the owner has not set to `announce` to the team page.
- Deleting a note, a release or a choice event to make a release work.
- Editing another author's note; save a choice instead.
