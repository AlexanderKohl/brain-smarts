# CI is set up when a code repository is created, not later

Read `/CONTRACT.md` first. This proposal adds one bullet to `SMART-RULE-0042` in `/RULES.md` and
widens that rule's `Applies when`. It is a small additive amendment, so the rule keeps its
identifier (CONTRACT §13.2). `/CORE-RULES.md` carries the rule's table row and is regenerated by
`core.py build`; it is never edited by hand. The development skill gains one line that points at
the rule.

## Summary in plain language

`SMART-RULE-0042` says a code repository runs the code map's checks in its CI on every push. It
does not say when CI is set up, so a repository can be built for weeks with none: one project had
reached version 0.21.0 and 179 tests before it got a CI run, and only because a task asking for it
had been waiting on the board.

Under this proposal CI is part of creating the repository. The first commits of a new code
repository add the CI run, and feature work starts once that run has passed. A repository the
brain meets that has code and no CI gets it before the next feature.

## Current wording

`/RULES.md`, the row of `SMART-RULE-0042` in the index, column `Applies when`:

> setting up or changing a code repository's CI, or when a code-map check fails

`SMART-RULE-0042 – Code repositories run the code map's checks`, four bullets, unchanged by this
proposal:

> - A code repository the brain works on runs the code map's checks in its CI on every push: no
>   import cycle among modules loaded at start-up, every UI call reaches a backend route, every
>   environment variable read is in an example env file, the code names only database columns its
>   models or tables define, and code files keep within their size (`SMART-RULE-0041`). A new
>   finding fails the push.
> - A repository adopts the checks by recording the findings it already has
>   (`code-map record --adopt`); those do not fail it, and each is fixed or kept as a known finding
>   on purpose.
> - The interface check is optional (a repository keeps an interface record only if it wants
>   one); the settings check reports and never fails.
> - CI takes the code map from the brain's mechanics at a fixed commit, raised on purpose, so a
>   change to the code map cannot break a repository's build unseen.

## Proposed wording

The index row's `Applies when` becomes:

> creating a code repository or giving one its remote; setting up or changing a code repository's
> CI; when a code-map check fails

A fifth bullet is added after the four:

> - CI is part of creating the repository, not a later task. When a code repository gets its
>   remote, the commit that first puts code in it, or the one straight after, adds the CI run: the
>   project's tests, even while there is only one, and the code map's checks, adopted while there
>   is nothing yet to adopt. Feature work begins once that run has passed. A repository the brain
>   starts work in that has code and no CI gets it before the next feature, and the agent says so
>   instead of filing it as a task for later.

`/shared/skills/product-development/SKILL.md`, *Workflow*, step 4, one item added to the list:

> - set up CI when the repository is created, before the first feature (`SMART-RULE-0042`)

## Reason

The owner's instruction of 17 November 2026: CI reached a project late in its development, so the
development skill needs a rule to set CI up as soon as something gets a GitHub repository. The
checks are cheapest to adopt when the repository is empty: nothing has to be recorded as a known
finding, and every later change is checked from the start.

## Scope and consequences

- Every code repository the brain creates or starts work in. A repository with no code (documents
  only) is not a code repository and is unaffected.
- A new project spends its first minutes on a workflow file and one passing run before any
  feature.
- An existing repository without CI gets it at the next piece of feature work there, not all at
  once across every repository.

## Risks and migration

- **A host without GitHub Actions.** The rule says "the CI run", not a product: the same checks
  run in whatever CI the repository's host offers.
- **Private mechanics.** CI fetches the code map from the mechanics repository; where an owner's
  copy of it is private, the workflow needs a read token for it. The code map's skill says how.
- **Existing repositories without CI** are found when work next starts in them. No sweep is
  proposed.
