# Ask about goals and values before designing, never about means

Read `/CONTRACT.md` first. This proposal adds one bullet to `SMART-RULE-0044` in `/RULES.md`. It
is a small additive amendment, so the rule keeps its identifier (CONTRACT §13.2). `/CORE-RULES.md`
carries the rule verbatim and is regenerated by `core.py build`; it is never edited by hand.

## Summary in plain language

Today an agent names the outcome behind a request and offers a bigger version of it
(`SMART-RULE-0044`), and asks nothing when a safe default exists (`SMART-RULE-0010`). Neither rule
says what to do when the work is open – a new project, or a task whose design is left to the
agent – and the goals or the values behind it could be read in more than one way. The agent then
either guesses the goals, or asks about methods the user has no reason to decide.

Under this proposal the agent asks about goals and values in that case, before it designs: what
the work is for, whom it serves, and what matters more when two aims conflict. It does not ask how
to achieve them. A task that is already spelled out gets no extra questions.

## Current wording

`/RULES.md`, `SMART-RULE-0044 – Raise the ambition of every request`, three bullets:

> - At the intake of every request, the agent applies `/shared/skills/raise-ambition/`: it names
>   the outcome behind the request and checks whether a bigger version would serve the user better
>   – one that reaches higher (an outcome kept true, not a task done once), deeper (an expert's
>   methods and a harder, measurable target) or wider (other fields and roles, including an
>   adversarial reviewer). The user is the person whose request it is: the owner, or a
>   collaborator working in a shared project.
> - When a bigger version would serve the user better, the agent's clarifying question offers it
>   as option 1, marked recommended, with what it would take; the request as asked is option 2.
>   When no question is otherwise needed, the agent does what was asked and adds one line naming
>   the bigger version.
> - The agent never widens the work without the user's yes, does not repeat a bigger version the
>   user declined for the same request, and keeps the suggestion to a few lines. Safety, cost,
>   side-effect and governance rules are unchanged.

## Proposed wording

The three bullets stay as they are. A fourth is added after them:

> - When a request starts a project, or leaves the design open, and the goals or the values behind
>   it are uncertain or could be read in more than one way, the agent asks about those before it
>   designs: what the work is for, whom it serves, and what matters more when two aims conflict.
>   It does not ask how the goals should be achieved; that is the agent's to work out. Each
>   question carries a suggested answer (`SMART-RULE-0010`), and the questions arrive with every
>   part of the work they do not block already done. A task whose outcome is already spelled out
>   gets no such questions.

The rule's row in the index of `/RULES.md` and its `Applies when` (`always`) are unchanged.

## Reason

An owner asked an agent for options on how several brains should share one project, and told it
to ask "about the goals and underlying values of the project, not about how those goals will be
achieved". Six questions of that kind, each with a suggested answer, were answered in one line and
settled the design: one of them ruled out the option the agent would otherwise have recommended.
Questions about means would not have done that, and no questions would have produced a design
built on a guess.

## Scope and consequences

- Every agent, in every brain that uses the mechanics, on requests that start a project or leave
  the design open. Spelled-out tasks, fixes, lookups and answers are untouched.
- The first reply to an open request may carry a short list of questions where it carried none
  before. Work the questions do not block still goes ahead.
- `SMART-RULE-0010` is unchanged: no invented questions, a suggested answer on each, one question
  at a time in voice mode.

## Risks and migration

- **More questions than the work deserves.** The bullet applies only when the goals or values are
  uncertain or ambiguous, and exempts spelled-out tasks. If agents still over-ask, the wording is
  tightened by a further amendment.
- **Overlap with the product-development process** (`SMART-RULE-0016`), whose early stages also
  establish goals. This bullet covers the intake of any open request, including ones that are not
  software; where the product-development process applies, its own stage does the asking and this
  bullet adds nothing.
- No migration: nothing existing changes.

## Rollback

Revert the commit that applies this proposal and run `core.py build`. The rule returns to its
three bullets.

## Validation

- `core.py build` regenerates `/CORE-RULES.md` with the fourth bullet, and the repository
  preflight passes on the mechanics.
- The next request that starts a project receives goal and value questions with suggested
  answers, and none about method.

The owner accepts or declines `PROPOSAL-ask-goals-before-design` as one answer. On acceptance the
